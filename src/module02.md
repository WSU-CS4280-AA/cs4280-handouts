## Raster vs. Vector

A **raster image** is a grid of sampled pixel values—for example, a
photograph, rendered image, or texture. A **vector image** is a
mathematical description of lines, curves, and fills that is rasterized
into pixels for display.

A raster image has a fixed native pixel grid, so enlarging it requires
resampling data that were not originally captured. A vector description
can be rasterized at the requested display resolution, although details
such as stroke widths, filters, and embedded raster assets can still
introduce practical limits.

## Pixels, the Grid, and Memory Layout

A **pixel** is one discrete sample associated with an image-grid location,
not literally a tiny square. When an image is displayed, the renderer
commonly visualizes each sample over a small screen area. The distinction
will matter when we discuss reconstruction and antialiasing in Week 6.

Pixels are stored in **scanline order**: row by row, left to right, top to
bottom. Since `ImageData.data` is a flat `Uint8ClampedArray`, the byte
offset of pixel ${tex`(x, y)`} in an image of width ${tex`W`} is:

${tex.block`\text{offset}(x,y) = (y \cdot W + x)\cdot C`}

Here, ${tex`C`} is the number of bytes per pixel. For Canvas `ImageData`,
${tex`C = 4`} because every pixel stores red, green, blue, and alpha.
Equivalently:

${tex.block`\text{offset}(x,y) = 4(y \cdot W + x)`}

This is an **interleaved** layout: `R, G, B, A` for one pixel, immediately
followed by `R, G, B, A` for the next. A **planar** layout instead stores
all red values, then all green values, then all blue values; planar layouts
are common in video-processing pipelines. Move your mouse over the image
below to inspect a pixel. The highlighted cell's coordinates, byte offset,
and raw RGBA bytes update live.

## The RGB Model and Bit Depth

Human color vision is approximately **trichromatic**: three overlapping
cone-response classes, conventionally called L, M, and S, make it possible
to match many perceived colors with three primary light channels. RGB is
therefore a useful engineering representation, but a particular RGB color
space such as sRGB covers only a limited **gamut** of visible colors.

Each channel's precision is its **bit depth**. With ${tex`n`} bits, one
channel can represent ${tex`2^n`} distinct values.

```js echo
const rgbForm = view(Inputs.form({

```

for ${tex`256^3`} possible RGB triples. Drag `bits` toward 1 or 2 and the

channel, its RGBA storage has ${tex`256^4`} possible channel tuples, although
alpha controls opacity rather than the underlying RGB color.

## Linear Light, sRGB, and Gamma

A raw triple such as `(0.5, 0.5, 0.5)` is incomplete: its meaning depends
on the color space and transfer function attached to it. The distinction
that matters most for graphics is between **linear-light RGB** and **sRGB**.

- In linear-light RGB, numerical values are proportional to physical light.
  Lighting, averaging, interpolation, filtering, and physically meaningful
  compositing should be performed in this space.
- sRGB is a nonlinear encoding used by most ordinary image assets and
  displays. It allocates more code values to darker tones, where the visual
  system is more sensitive to relative differences.

The exact sRGB transfer function is piecewise: it is linear near black and
nonlinear elsewhere. For teaching and intuition, it is common to use a
power-law approximation with gamma near 2.2:

${tex.block`C_{\mathrm{encoded}} \approx C_{\mathrm{linear}}^{1/\gamma}
\qquad
C_{\mathrm{linear}} \approx C_{\mathrm{encoded}}^{\gamma}`}

These equations are an approximation, not the literal definition of sRGB.
Use exact sRGB encode/decode functions in production code when color
accuracy matters.

```js echo
const gammaValue = view(Inputs.range([0.1, 3.2], {value: 2.2, step: 0.05, label: "approximate γ"}));
```

The two curves below are decode ($C_{\mathrm{linear}} = C_{\mathrm{encoded}}^{\gamma}$)
and encode ($C_{\mathrm{encoded}} = C_{\mathrm{linear}}^{1/\gamma}$) for the
gamma selected above, plotted against the identity line ($\gamma = 1$, no
change). Decode bows above the diagonal—it brightens—while encode bows
below it—it darkens—and the two are mirror images of each other across the
diagonal, since one undoes the other.

The encoded ramp looks brighter even though it represents the same ordered

averaging sRGB byte values is not the same as averaging light.

  }

    return {

      g: raster.gammaDecode(c.g / 255),
      b: raster.gammaDecode(c.b / 255)
    };
  }

    return {
      r: Math.round(raster.gammaEncode(c.r) * 255),
      g: Math.round(raster.gammaEncode(c.g) * 255),

  const bLin = toLinear01(b);
  const midLin = {
    r: (aLin.r + bLin.r) / 2,

The naive midpoint is too dark because sRGB encoding is nonlinear. For
color arithmetic such as averaging, interpolation, filtering, and mipmap
generation, use the same pattern: **decode to linear light, do the math,
then encode once for display or storage.**

## Alpha and Compositing

**Alpha** is a fourth channel that records opacity. In normalized notation,
${tex`\alpha = 1`} is fully opaque and ${tex`\alpha = 0`} is fully transparent.

For general source-over compositing of straight-alpha colors in linear
light — with a foreground (source) layer composited over a background
(destination) layer — the output alpha is:

${tex.block`\alpha_{out} = \alpha_f + \alpha_b(1-\alpha_f)`}

and the output color is:

${tex.block`C_{out} =
\frac{C_f\alpha_f + C_b\alpha_b(1-\alpha_f)}{\alpha_{out}}
\qquad \text{when } \alpha_{out} > 0`}

If the background is opaque, ${tex`\alpha_b = 1`} and the expression
simplifies to the familiar form:

${tex.block`C_{out} = C_f\alpha_f + C_b(1-\alpha_f)`}

The grass image below is opaque, so the interactive example uses this
simplified case. As in the preceding section, the color arithmetic should
conceptually happen in linear light; real browser and asset pipelines may
apply color management differently, so production renderers should track
color spaces explicitly.

The foreground is a motorcycle with a soft drop shadow and a genuine
per-pixel alpha channel (freesvg.org / OpenClipart, Public Domain / CC0),
composited over a photograph of grass (Kurt Kaiser, CC0, Wikimedia
Commons).

**Straight alpha** stores color independently of opacity: a pixel stores
${tex`(C, \alpha)`}. **Premultiplied alpha** stores color already multiplied
by alpha: ${tex`(C' = \alpha C, \alpha)`}. Therefore, a correctly
premultiplied pixel with ${tex`\alpha = 0`} has zero stored RGB. By contrast,
straight-alpha images may retain arbitrary RGB values in fully transparent
pixels.

## Compression: A Toy Run-Length Encoder

**Lossless** formats preserve the original samples exactly. PNG combines
filtering with DEFLATE compression; GIF uses LZW compression; and simple
**run-length encoding** (RLE) is a useful toy example of redundancy-based
lossless compression. **Lossy** compression discards some information in
exchange for much smaller files. In common JPEG workflows, images are
transformed into luminance and chroma components; chroma may be subsampled,
and transform coefficients are quantized more aggressively at frequencies
where errors are often less noticeable.

Here is a run-length encoder that compresses one red-channel row of the
test image:

```js echo
function rleEncode(values) {
  const runs = [];
  for (const value of values) {
    const last = runs[runs.length - 1];
    if (last && last.value === value && last.count < 255) last.count++;
    else runs.push({value, count: 1});
  }
  return runs;
}
```

```js echo
const rleRow = view(Inputs.range([0, testImage.height - 1], {
  value: 5,
  step: 1,
  label: "row to compress"
}));
```

```js echo
(() => {
  const values = [];
  for (let x = 0; x < testImage.width; x++) {
    values.push(raster.getPixel(testImage, x, rleRow).r);
  }

  const runs = rleEncode(values);
  const originalBytes = values.length;
  const encodedBytes = runs.length * 2;
  return html`<pre>row ${rleRow}, red channel: ${values.length} pixels
runs: ${runs.length} (as [value × count] pairs, first few: ${runs.slice(0, 6).map((r) => `${r.value}×${r.count}`).join(", ")}...)
original: ${originalBytes} bytes → simplified RLE model: ${encodedBytes} bytes (${(encodedBytes / originalBytes * 100).toFixed(0)}% of original)</pre>`;
})()
```

Try different rows. Rows with long runs of similar values compress well;
rows crossing the sun or tree edges have more runs and compress worse. This
is a deliberately simplified one-channel model: a real RGBA image format
must encode all channels, metadata, and usually additional prediction or
entropy-coding steps. The example isolates the central idea that achievable
compression depends on actual redundancy.

## Point Operations

A **point operation** computes each output pixel using only the
corresponding input pixel. This makes point operations trivially parallel
and closely related to per-fragment GPU computation.

| Operation | Formula |
|---|---|
| Brightness | ${tex`I_{out} = I_{in} + b`} |
| Contrast | ${tex`I_{out} = (I_{in}-128)\cdot c + 128`} |
| Inversion | ${tex`I_{out} = 255 - I_{in}`} |
| Per-channel threshold | ${tex`I_{out} = 255 \text{ if } I_{in}\geq t \text{; otherwise } 0`} |

Here we use 8-bit channel values, so the midpoint is 128. In normalized
floating-point color, the equivalent midpoint is 0.5. Values outside the
representable 8-bit range are clamped to 0 or 255 when written into
`ImageData`; that clipping is why large brightness shifts or high contrast
can create spikes at the endpoints of a histogram.

```js echo

  invert: Inputs.toggle({label: "invert"}),

```

## Neighborhood Operations and Filtering

A **neighborhood operation** computes each output pixel from a small region
of input pixels. A **kernel** is a small table of weights slid across the
image.

The implementation below uses **cross-correlation**:

${tex.block`I_{out}(x,y) = \sum_{i,j} K(i,j)\cdot I_{in}(x+i,y+j)`}

True mathematical convolution flips the kernel before applying it. Image
processing and graphics APIs often call both operations “convolution.” For
symmetric kernels such as box blur, sharpen, and the edge kernel below,
the results are identical; for an asymmetric kernel such as emboss, the
flip changes the apparent emboss direction.

  "Edge detection": [0, -1, 0, -1, 4, -1, 0, -1, 0],

};

A normalized 3×3 box blur averages the center pixel and its eight immediate
neighbors, smoothing detail. Sharpen and edge detection are nearly the same
kernel: sharpen uses a center weight of 5, preserving the original while
adding high-frequency detail; the edge kernel uses a center weight of 4, so
constant channel values cancel in flat regions and local color or intensity
changes remain. Emboss uses lopsided positive and negative weights to turn
edges into raised ridges, as though light were raking across the image.

## Sampling Preview: Aliasing

A raster image is a **sampled signal**: it represents a continuous scene
only at grid locations. Detail that varies too quickly for the sample grid
causes **aliasing**.

Below, the image is decimated by retaining one sample every ${tex`N`} pixels,
then reconstructed by repeating each retained sample over an ${tex`N × N`}
block. We will cover better reconstruction and full pixel coverage in Week
6, but the aliasing effect is worth seeing now.

```js echo
const sampleStride = view(Inputs.range([1, 10], {
  value: 1,
  step: 1,
  label: "sample every Nth pixel"
}));
```

        ? "#111"

    }
  }

  sampled.height = size;

  sctx.imageSmoothingEnabled = false;

can develop false low-frequency patterns—sometimes moiré-like bands or
ripples—rather than a faithful coarser checkerboard. The original signal
contains frequencies above half the new sampling frequency, the **Nyquist
frequency**, so the retained samples cannot represent the detail
unambiguously. Filtering before downsampling reduces this problem by
removing frequencies the coarser grid cannot represent.

## Raster Images in the Graphics Pipeline

Each of the following is structurally a raster grid. They differ in what
each sample stores and how later stages use it.

| Raster buffer | Stores | Role |
|---|---|---|
| **Frame buffer** | Final RGB(A), often 8-bit sRGB | Output sent to the display |
| **Texture** | Color (often sRGB), or normal/roughness data (linear, non-color) | Input sampled onto a surface through UV coordinates |
| **Shadow map** | Depth from the light's point of view | Input to occlusion tests |
| **G-buffer** | Per-pixel normal, depth, albedo, and material data | Intermediate output from deferred rendering's first pass |
| **Environment map** | Incoming light from all directions, often HDR | Input to image-based lighting |

The same `getPixel`, `mapPixels`, and neighborhood-filter operations from
this page apply to all of these. A shadow map is an image whose sample value
happens to represent depth rather than visible color.

## Summary

- **Pixels and storage** — samples are stored in scanline/row-major order;
  Canvas `ImageData` uses an interleaved RGBA layout.
- **RGB and bit depth** — RGB leverages approximate trichromacy, but each
  RGB space has limited gamut; insufficient bit depth produces quantization
  and banding.
- **Linear light and sRGB** — use exact sRGB conversion when needed, and
  perform color arithmetic in linear light rather than directly on encoded
  byte values.
- **Alpha compositing** — source-over blending includes both output color
  and output alpha; straight and premultiplied alpha must not be mixed.
- **Point operations** — brightness, contrast, inversion, and per-channel
  thresholding act independently on each input pixel, with clamping at the
  8-bit range.
- **Neighborhood operations** — kernel-based filtering provides blur,
  sharpen, edge detection, and emboss; the implementation shown is
  cross-correlation, commonly called convolution in practice.
- **Compression** — lossless and lossy formats exploit different kinds of
  redundancy or perceptual tolerance; the RLE example isolates repeated
  channel values.
- **Sampling and aliasing** — insufficient sampling produces false patterns
  and lost detail; filter before downsampling to reduce aliasing.
- **GPU images** — frame buffers, textures, G-buffers, shadow maps, and
  environment maps are all raster grids whose samples store different data.
